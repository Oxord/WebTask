## Как запустить

```bash
docker compose up -d --build          # поднять web + db + db_test
docker compose exec web composer install
docker compose exec web vendor/bin/phpunit   # 202 теста
./scripts/smoke.sh                     # проверка маршрутов и прав
```

Сайт — http://localhost:8081, админка — http://localhost:8081/admin.

> **Порт 8081, а не 8080.** На 8080 у пользователя работает не связанный с этим
> проектом стек `projectarena`, поэтому порт вынесен в `WEB_PORT` в `.env`.

## Архитектура

```
public/index.php      front controller: таблица маршрутов, централизованная
                      проверка CSRF на всех POST, обработка 404/403/500
src/Core/             Router, Database (PDO), Request, Response, View, Session,
                      Csrf, Validator, Auth, Cache, Config
src/Repository/       User, Category, Product, Promotion, Order, Review, ContactMessage
src/Service/          Auth, Cart, Order, Review, Stats, Upload
src/Middleware/       RequireAuth, RequireRole, RequireGuest
src/Controller/       публичные + Admin/**  (трейт RendersPage готовит auth/cartCount)
views/                layouts/{main,admin}, partials/, pages/, admin/
db/                   01_schema.sql (9 таблиц), 02_seed.sql (демо-данные)
tests/                Unit/ (мокированные) + Integration/ (отдельная БД db_test)
```

Ключевые решения:
- **Корзина в сессии** — ТЗ требует добавление/просмотр/редактирование/оформление,
  межсессионная синхронизация не нужна.
- **CSRF проверяется в одном месте** во front controller, а не в каждом контроллере —
  контроллер физически не может «забыть» проверку. Поле называется `_csrf`.
- **Интеграционные тесты — на отдельной БД** `db_test` (только схема, без seed),
  каждый тест в транзакции с откатом; поэтому демо-данные можно менять свободно.
- **Списание остатков — внутри транзакции заказа** (см. ниже).

## Что было найдено и исправлено

### Баги, найденные при сборке
1. **CSRF не работал совсем.** `Csrf::field()` отдавал поле `_csrf`, а front controller
   проверял `_token` — не совпадало никогда. Агенты обошли это, вставляя в каждую форму
   оба поля. Приведено к одному имени `_csrf`, дубли убраны.
2. **Docker-образ не собирался** — `pecl clear-cache` падал в `Dockerfile`. Строка убрана.

### Замечания code review
3. **Overselling (критично).** Остатки списывались *после* коммита заказа, отдельными
   `UPDATE ... GREATEST(stock-qty, 0)`. Два одновременных заказа на последнюю единицу
   оба проходили, а сбой посреди цикла оставлял заказ с несписанными остатками.
   Теперь `decrementStock()` содержит условие `stock >= qty` и возвращает `false`,
   а списание выполняется внутри транзакции заказа через колбэк
   `OrderRepository::create()`. Не хватило товара — откатывается весь заказ,
   корзина не очищается. Покрыто 5 тестами.
4. **SQL в контроллерах.** Админ-контроллеры выполняли свои запросы через
   `Database::connection()` в обход репозиториев. Фильтр по категории перенесён в
   `ProductRepository::paginateAdmin()`, `is_active` — в `UserRepository::update()`.
5. **Layout ходил в БД.** `views/layouts/main.php` сам создавал `Auth`/`CartService`.
   Для страницы ошибки это опасно: её рендерит front controller без контроллера,
   то есть layout лез в БД в момент, когда БД могла быть причиной ошибки.
   Вынесено в трейт `App\Controller\RendersPage`.
6. **Демо-отзывы выглядели сломанными** — все три избранных отзыва были от одного
   человека, а авторами отзывов были админ и модератор. Добавлено 5 покупателей,
   отзывы распределены между ними.

### Проверено вживую (не только тестами)
- Матрица ролей: модератор → 403 на `/admin/products`, `/admin/users`, `/admin/promotions`,
  не может сменить статус заказа (403 даже с валидным CSRF), формы смены статуса не видит;
  пользователь → 403 на всей админке; гость → 302 на логин.
- CSRF: POST без токена и с неверным токеном → 403.
- Сквозной заказ: остаток 25 → 23, заказ и позиции записаны верно, страница успеха 200.
- Чужой заказ по подставленному id → 404 (проверка владельца).
- Фильтры админки: по категории, по строке и комбинированно.
- Деактивированный пользователь не может войти.

## Что осталось за рамками

Это осознанные упрощения, не блокеры по ТЗ:

- **Оплата не подключена** — ТЗ её не требует, заказ оформляется со статусом `new`.
- **`/account/orders` без пагинации** — `OrderRepository::forUser()` отдаёт весь список.
  Для демо-объёмов нормально, при росте истории заказов стоит добавить.
- **N+1 в списке отзывов админки** — автор и товар подгружаются по одному на строку
  (20 строк на страницу). Лечится join-методом в `ReviewRepository`.
- **Карта на «Контактах»** — iframe OpenStreetMap с координатами центра Москвы
  (плейсхолдер, реального адреса магазина нет). Единственный внешний ресурс на сайте.
- **Юридические ссылки в подвале** — заглушки (оферта, политика, ИНН/ОГРН).
- **`.env` не версионируется** — в репозитории только `.env.example`, а значения по
  умолчанию продублированы в `docker-compose.yml`, поэтому свежий клон поднимается без
  подготовки. Пароли БД в шаблоне — локальные для docker-сети; для реального
  развёртывания их нужно заменить.
